# Ask-Advisor 实验方案

本页整理自项目原方案，保留研究设计第 1–13 节。以下 pilot 与正式实验均为计划。已完成的 make 单样本属于功能测试，详见 [make 复盘](make-trial.md)。运行环境和恢复步骤见[双机交接](handoff.md)。

**阅读时请区分原定设计与现有实现。** 本轮功能测试已冻结 p_yes ≥ 0.70，从第 3 个不同工具反馈起评分，每任务最多调用 3 次。下文的候选阈值比较属于 pilot 设计。正式 A 组计划记录影子评分；已运行的普通 Terminus 2 基线不应直接当作完成该设计的 A 组。第 8–9 节描述预期的 Advisor 上下文和输出，当前代理实际发送的判断问题及上下文截取方式见 [chat_interceptor.py](../code/ask_advisor_runner/chat_interceptor.py)。

## 一、研究目标

验证以下三个问题：

1. 云端 Advisor 的建议是否能够提高本地 Qwen 完成长程任务的成功率？
2. 本地 Qwen 通过 System One 能否识别合适的求助时机？
3. 在每次任务最多调用 Advisor 3 次的条件下，性能改善是否值得增加的延迟和费用？

第一阶段只研究“同步建议”：

- Advisor 不直接操作终端；
- Advisor 不接管任务；
- Advisor 只返回建议；
- 本地 Qwen 接收建议后继续执行。

KV cache 优化、异步调用和云端接管不属于本阶段。

## 二、实验版本边界

正式实验开始后不得根据中途结果修改：

- System One 问题文本；
- 触发阈值；
- 检测频率；
- Advisor 上下文；
- Advisor 提示词；
- 每次运行的调用上限；
- Qwen 和 Advisor 模型参数。

如需修改，必须创建新版本，并重新执行受影响的 pilot。

## 三、实验条件

### A 组：本地 Qwen 基线

- 本地 Qwen 独立执行任务。
- 不调用 Advisor。
- System One 正常运行，但仅进行影子判断。
- 记录每次判断的分数和假设触发时间。
- 影子判断结果不得注入 Qwen 上下文。

目的：测量纯本地 Qwen 表现，并获得不受 Advisor 干预的 System One 判断轨迹。

### B 组：确定性规则触发 Advisor

**当前状态：延期，不纳入第一批 pilot 和当前正式主比较。**

- 使用旧版已经冻结的停滞规则。
- 规则命中后由系统同步调用 Advisor。
- Advisor 只提供建议，不直接执行操作。
- 建议注入 Qwen 后，由 Qwen 继续执行。
- 每次运行最多调用 3 次。
- 同一停滞事件只能调用一次；发生实质进展后才允许重新武装。

目的：验证在可审计、确定性时机提供 Advisor 建议是否有效，并作为 System One 触发器的参照。

### C 组：System One 自动触发 Advisor

- 每个合格检测点调用本地 System One。
- System One 判断“此时请求 Advisor 是否可能实质提高任务成功概率”。
- 达到预先冻结的阈值后，由系统同步调用 Advisor。
- Advisor 只提供建议，不直接操作环境。
- 每次运行最多调用 3 次。
- 同一事件不得重复调用；发生实质进展后才重新武装。

目的：验证本地模型能否自动选择有价值的求助时机。

## 四、Pilot 设计（老师确认后的 A/C 优先方案）

选择 5 个固定的 Terminal-Bench 2.1 任务。

每个任务运行：

- A 组 1 次；
- C 组 1 次。

共计：

```text
5 个任务 × 2 组 × 1 次 = 10 次首批 pilot 运行
```

这 10 次运行满足老师建议的“首批 10 至 20 个样本”的下限。如果 10 次不足以验证链路稳定性，可在查看正式实验结果之前，将 pilot 扩展为 10 个任务、A/C 各 1 次，共 20 次。是否扩展必须先记录理由并冻结新增任务列表，不能根据哪组成绩更好临时决定。

Pilot 仅用于：

- 验证完整链路；
- 检查 System One 输出是否有效；
- 冻结正式阈值；
- 检查 Advisor 建议能否正确注入；
- 检查数据和截图是否完整；
- 比较 A 组影子判断与 C 组实际触发的位置；
- 验证辅助判断能否解释触发属于“停滞救援”还是“关键步骤预防”。

Pilot 不进入正式效果统计。

Pilot 任务原则上不进入正式任务；如必须重合，正式阶段必须使用全新容器、上下文和运行 ID。

## 五、正式实验设计

如果 pilot 通过，建议正式实验只保留核心比较：

- A 组：本地 Qwen，无 Advisor；
- C 组：System One 自动触发 Advisor。

运行规模：

```text
正式运行次数 = 纳入任务数 × 2 组 × 每组 5 次
```

B 组当前延期，不进入本轮正式实验。若后续需要正式比较“确定性规则触发”和“System One 触发”，必须新建实验版本并单独安排 B 组，不得混入已经开始的 A/C 批次。

## 六、System One 判断设计

### 6.1 主判断问题

每次只使用一个问题决定是否调用：

```text
根据任务目标和截至当前的可观察执行轨迹，
现在请求云端 Advisor 提供一次建议，
是否很可能实质提高本次任务最终成功的概率？

回答：YES 或 NO
```

系统保存：

- `p_yes`
- `p_no`
- 最终标签
- 判断延迟
- 输入 Token
- 缓存命中信息
- 检测步骤号

只有 `p_yes` 达到冻结阈值时才允许触发。

### 6.2 辅助判断

老师同意增加辅助判断。辅助判断同时记录但不参与触发：

```text
当前执行是否已经停滞？
下一步是否属于高风险或复杂的关键步骤？
```

辅助结果用于区分：

- 解救型求助：已经停滞；
- 预防型求助：尚未停滞，但即将进行关键决策。

正式实验前必须明确只有主问题控制调用，防止多个条件造成不可解释的触发。

辅助判断的用途是解释主判断为什么倾向求助：

- “当前是否已经停滞”用于识别解救型求助；
- “下一步是否属于高风险或复杂的关键步骤”用于识别预防型求助；
- 两项结果都属于影子诊断信息，即使为 YES，也不能单独触发 Advisor。

### 6.3 检测时机

从第 3 个工具步骤结束后开始检测。

之后仅在以下事件后检测：

- 新的命令或工具结果返回；
- 测试结果发生变化；
- 代码修改完成；
- 错误类型发生变化；
- Qwen 准备进行新的实质行动。

以下情况不检测：

- 单纯等待或轮询；
- 完全重复、没有新增信息的输出；
- Advisor 请求仍在处理中；
- 当前事件已经调用过 Advisor；
- 已达到 3 次调用上限。

这里的“不检测”是指不再发起一次新的、可能触发调用的在线判断；相关事件仍写入普通轨迹日志。达到 3 次调用上限后，继续进行低优先级影子记录，以评估 3 次上限是否过低，但不得发起第 4 次 Advisor 调用。

### 6.4 阈值冻结

Pilot 开始前先设置候选阈值，例如：

```text
0.50、0.70、0.85
```

A 组影子判断可以同时计算这些候选阈值会产生多少次触发，但不得调用 Advisor。

Pilot 结束后按以下顺序选正式阈值：

1. 不应让大多数运行迅速耗尽 3 次额度；
2. 优先保留经人工盲审认为有价值的触发；
3. 兼顾漏掉明显困难时刻的情况；
4. 一旦选定，正式实验期间不得调整。


## 七、事件去重与重新武装

每次触发生成唯一的：

```text
trigger_id
event_id
```

触发后，该事件进入“已处理”状态。

只有出现以下任一实质进展后才重新武装：

- 新增有效代码修改；
- 至少一项此前失败的测试通过；
- 错误类型实质变化；
- 阻塞对象或根因发生变化；
- 完成一个明确子目标。

以下情况不算实质进展：

- 重复相同命令；
- 只改写解释但没有行动；
- 相同错误换一种表述；
- 无关文件发生变化；
- 单纯等待。

达到 3 次 Advisor 调用后，System One 继续进行影子判断和记录，但不再调用 Advisor。

## 八、发送给 Advisor 的上下文

Advisor 只能接收解决当前状态所需的信息：

1. 任务公开说明；
2. 当前环境和允许使用的工具；
3. 最近 8 个可观察步骤；
4. 已尝试方法的结构化摘要；
5. 当前错误或失败测试；
6. 当前代码 diff 摘要；
7. 已收到的 Advisor 建议及其后续结果；
8. 本次求助的具体问题。

不得发送：

- 参考答案；
- 隐藏测试内容；
- grader 实现；
- API key、SSH 密钥、密码或 token；
- 与任务无关的私人信息；
- 未公开的人工解题提示。

默认不发送 Qwen 的隐藏推理过程，只发送可观察的操作、结果及结构化摘要。

## 九、Advisor 输出格式

Advisor 应返回：

```text
1. 对当前问题的判断
2. 最可能的根因
3. 建议执行的下一步
4. 如果该步骤失败，应检查什么
5. 建议涉及的风险或不确定性
```

Advisor 不得宣称已经执行命令，也不得直接控制终端。

注入 Qwen 时必须添加明显边界：

```text
[EXTERNAL_ADVISOR_SUGGESTION]
……
[/EXTERNAL_ADVISOR_SUGGESTION]
```

## 十、任务和运行控制

所有组保持一致：

- Terminal-Bench 2.1 修订版本；
- Harbor 版本；
- 任务容器镜像；
- Qwen 版本和量化方式；
- Qwen 采样参数；
- Token 和时间预算；
- CPU、GPU 及内存限制；
- 工具权限；
- 单任务最大步骤数；
- 单任务超时；
- 初始工作区状态。

A/C 应按任务和重复编号配对。组别运行顺序随机化或交替平衡，防止服务器时间、缓存或负载造成系统性偏差。

每次运行使用唯一的：

```text
tb21-{task_id}-{group}-{repeat}-{timestamp}
```

## 十一、动作类型

每个 Agent 步骤标注为：

- `write_edit`
- `read_search`
- `diagnose_reproduce`
- `test_validate`
- `discover_navigate`
- `wait_poll`

用于分析 Advisor 调用是否集中在真正困难的步骤，以及不同动作类型上的建议效果。

## 十二、主要与次要指标

### 主要指标

- A/C 任务通过率差异；
- A/C 平均 Harbor Reward 差异。

### 次要指标

- 总耗时；
- Agent 步骤数和工具调用数；
- Qwen Token；
- System One 监测开销；
- Advisor 调用次数、Token、费用和延迟；
- 触发后实质进展率；
- 每类动作的触发率和进展率；
- 误触发、漏触发和重复触发率；
- 达到 3 次上限后仍出现困难事件的比例。

不得只报告成功任务或平均值；必须保存并报告所有运行。

## 十三、Pilot 通过标准

只有同时满足以下条件才能进入正式实验：

1. 首批 10 次 pilot 均保存完整原始日志；如预先决定扩展到 20 次，则扩展运行也必须完整；
2. A 组没有实际调用 Advisor；
3. C 组调用上限为 3 次；
4. 同一事件没有重复调用；
5. 建议均正确注入；
6. Advisor 上下文不包含凭据或隐藏测试；
7. 所有触发均可回溯；
8. System One 分数和延迟均被记录；
9. Harbor 结果能够自动读取；
10. 不存在未记录的人工干预；
11. 已冻结正式阈值；
12. 已冻结正式任务、版本和统计方法。

任何桥接、日志或污染问题修复后，必须重跑受影响的 pilot。
